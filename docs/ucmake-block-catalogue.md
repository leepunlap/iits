## Block -> wire command, for the ones the lab already implements

The app's runtime handlers give the exact bytes; these are the ones wired into
`lab-device/ucmake_cli.js` and confirmed against the physical kit (2026-10-11):

| opcode | wire command | hardware result |
|---|---|---|
| `espMinSetDcMotor` | `A8 <PIN> 0 0 <OUT> 0` | motor ran at speed 100 |
| `espMinSetDcMotorStop` | `A8 10 3 0 0 0` | stopped |
| `espSetFourDigitDisplay` | `A10 <PIN> <OUT>` | showed 8888 |
| `esp32SetLedButtonSensor` | `A3 <PIN> 2 <INDEX> <0\|1>` | all four LEDs lit (HIGH is sent as 0) |
| `esp32ReadLedButtonSensorDigital` | `A3 <PIN> 1 <INDEX>` | held button read `1`, others `0` |
| `esp32ReadUltrasonicDistanceCm` | `A5 <PIN> 4` | **panics the firmware when no module is attached** |

UC-Mind300 (Firmata 2.5, not the CLI): motor 1 = PWM 10 + dir 9, motor 2 = PWM 5 + dir 6,
buzzer = pin 7, analog A0–A5 = pins 14–19; all verified on hardware.

## Known unknowns — do not assume these are settled

1. **Menu value sets are not reliably extracted.** A naive window over the minified source runs
   past the end of each menu array into the next getter and yields plausible-looking nonsense
   (e.g. a colour-sensor index menu "containing" baud rates). Any menu dump must come from
   brace-balanced parsing; none has been produced yet. The *names* of the menus are solid
   (`ucMakePorts`, `dcMotorM`, `ledButtonIndex`, `lineType`, `axis`, `irrecvIndex`, …).
2. **Reply semantics and units are unknown for every sensor read** — ultrasonic, colour,
   line follower (1/2/5-way + contrast), gyro, joystick, humidity, light, sound, rain, moisture,
   PIR, touch, IR, 36-encoder motor. Unresolved loose end: `A1 1 1 1` returns `180.00` on *both*
   boards and it is not known what that represents.
3. **Per-board function sets are not systematically mapped.** The ESP32-min family uses `A8` for
   DC motors, others use `A17`; the AVR (UC-Mind300) CLI command set has not been verified on
   hardware at all.
4. **Only four peripherals are hardware-verified** (display, DC motor, 4-LED module, buttons).
   Everything else is template-only.
5. **The panic surface is unmapped** beyond bad reads. Which writes are unsafe with out-of-range
   values is untested — the lab therefore validates before sending.

## How each block is actually executed — the finding that shapes the build

The 105 hardware blocks are **not one mechanism**. Reading each block's handler in the bundle:

| mechanism | blocks | examples | usable live? |
|---|---|---|---|
| **CLI text** (`send("A…")`) | 12 | all `espMin*` — motor, display, LED button, colour, ultrasonic, servo | ✅ verified on hardware |
| **Firmata OneWire SysEx** (`sendOneWireWrite`) | 31 | `setDcMotor`, `setFourDigitDisplay`, `setLedButtonSensor`, `setColorSensor`, `setUltrasonicColor` | ⚠️ needs a firmware exposing OneWire |
| **Arduino code generation** (upload only) | 34 | `setBuzzer`, `setSingleLedOutput`, `readGyroSensor`, `readJoystickSensor`, `readPIRReceived`, `readTouchReceived`, `readCompassSensor` | ❌ only after compiling + flashing |
| **Local / timers, no hardware command** | 28 | `start300timer`, `espdigital*`, `24GController*` | n/a |

So "all of them in Wonder Lab" needs a **hybrid executor**, which is exactly what UCMake itself does —
its realtime mode flashes a CLI firmware and talks text, and everything else it compiles into a
sketch and uploads (the upload log recorded two flashes when the motor program ran).

### The three execution paths the lab needs

1. **Realtime CLI** — implemented (`ucmake_cli.js`); the 12 hardware blocks of the L2 board, 4 verified.
2. **Realtime OneWire SysEx** — to implement; blocked on a firmware that advertises OneWire (neither
   shipped image does, so this may require the vendor's full link build).
3. **Compile-and-upload** — generate an Arduino sketch from the blocks (the bundle contains the
   vendor's own codegen, so the mapping block→source is recoverable), compile with `arduino-cli`,
   flash with `avrdude`/`esptool`. This is the only route for the 34 upload-only blocks.
